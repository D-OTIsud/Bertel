# Album photo — paquet de production ciblé

Le paquet reprend seulement le contrat photo/CRM indispensable depuis la base vivante du 5 novembre. Il ne déploie ni nouvelle base, ni Docker, ni migrations séjour/menu/horaires, ni préconditions génériques de collections, ni expéditeur email, ni activation IA.

`install.sql` est le seul fichier d’installation : préparation fermée + recette obligatoire dans une sous-transaction systématiquement annulée. Il s’exécute via **apply_migration**, une seule transaction et une seule entrée d’historique réelle. La garde XID précède toute DDL ; toute erreur de recette ou de comparaison publique annule l’installation entière. Aucun BEGIN/ROLLBACK imbriqué ni historique de migration factice. Ne pas appliquer `prepare.sql` seul.

La recette résout une fiche `is_test` déjà liée à un acteur de test et le compte superadmin existant unique. Une empreinte opérateur privée confirme exactement la sélection déjà revue ; aucun identifiant pilote n’est écrit en littéral dans le SQL. Le compte n’est lié à l’acteur que dans la sous-transaction annulée. Ce test est une recette SQL des rôles/portées réels, pas un login navigateur acteur. Aucun compte, lien, média, document, message, notification, changement d’ACL ou policy de recette ne reste après cette sous-transaction. Les compteurs CRM/notification, données pilote, ACL/fonctions et policies sont explicitement comparés avant/après. Les séquences PostgreSQL peuvent conserver des trous habituels après des transactions annulées.

Le writer office est épinglé : suppressions CAS avant les lignes, puis démotions avant promotions. Le reçu conserve la demande originale ; un snapshot invalide après une suppression annule tout. `review-office-final.sql` montre le corps final reconstruit pour la revue, sans être une procédure d’application autonome. Les nouveaux verrous de modération restent limités au circuit photo ; les writers commercial et horaires et leurs lecteurs ne changent pas.

La recette vérifie textes/classement, refus hors fiche, conflit office périmé, changements/suppression de principale avec ordre défavorable, rollback sur snapshot invalide, reçus idempotents, dépôt privé SQL, refus/recours CRM et autorisation d’aperçu, plafond vingt et remplacement sans place supplémentaire. Les octets de Storage, la route de signature, un login acteur et une vraie attente à deux connexions ne sont pas testés par ces appels SQL. Aucun octet n’est envoyé, aucune analyse ni email n’est déclenché. Le sender CRM générique reste interdit à authenticated ; les recours photo DEFINER l’utilisent comme propriétaire.

Les JSON publics sont capturés intégralement hors Git avec `public-snapshot.sql` : toutes les catégories publiées non-test disponibles, contexte sans uid/droit étendu. Le brut et sa projection v1 sont comparés séparément, sans ignorer de valeurs volatiles. La projection retire seulement les deux clés que la route v1 retire elle-même ; l’arbre clés/types brut conserve aussi leur présence/type. `compare-public-snapshots.py` produit le contrôle récursif incluant NULL et tableaux vides. `install.sql` exige la baseline privée et compare à nouveau fonctions et empreintes brutes/projetées après annulation du pilote, avant de pouvoir commettre le socle. Refaire cette capture après commit ; le root conserve les preuves HTTP/santé/journaux séparément.

Ordre suivi : revue et référence initiale → installation fermée avec recette annulée → déploiement et vérification de l’office compatible → déploiement de l’album en consultation → activation séparée. `close.sql` ferme les mutations photo ; il ne restitue pas les écritures office v1 après les policies R5. Le retour applicatif consiste à épingler puis reconstruire `75568b8` dans Coolify. Cette version compatible a été servie et vérifiée. Aucune image de retour instantané n’était proposée pour cette ressource Compose.

`build-sql-package.py` ne contacte aucune base ; il génère les fichiers depuis les sources relues et les preuves locales. `make-operator-payload.py` construit hors Git le payload via paramètres privés et sélection par empreinte. Le résultat `base-install-operator.private.sql`, les sorties JSON et traces de migration restent dans le dossier opérateur. **Ne pas exécuter migration fetch/pull vers le dépôt public sans anonymisation/revue des statements de l’historique.** Aucune clé ni mot de passe n’est nécessaire dans ces fichiers.
